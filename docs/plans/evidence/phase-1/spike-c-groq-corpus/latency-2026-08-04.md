## 1. The budget

PRD §5.4 *Performance targets* opens: *"These targets apply to preview and local authoring,
not production traffic."* The rows that govern query evaluation, verbatim:

| Operation | Target |
|---|---:|
| ID or slug preview query, warm | p95 under 1.5 seconds |
| Type-constrained list query, warm | p95 under 3 seconds |
| Preview refresh after edit | p95 under 2 seconds |

**§5.4 does define query-latency numbers, so none had to be invented.** Three things about
them are load-bearing for how this document reads:

1. They are **end-to-end** budgets for a warm preview query — base fetch over the network,
   overlay resolution, `groq-js` evaluation, serialisation, transport. This spike runs
   entirely in-process and measures a **strict subset** of that path. A local measurement can
   therefore *falsify* the budget (if the local part alone exceeds it) but can never *confirm*
   it. Every "within budget" below means "within budget in the part measured here, with the
   stated headroom left for everything else".
2. §5.4 budgets **time**; §22.6 bounds **work**; the PRD contains no conversion between them.
   The work budgets this suite gates on are therefore a **proposal** (§4.2) and are marked as
   such in the code.
3. *Preview refresh after edit* (2 s) is a workflow-level target spanning mutation
   acknowledgement plus re-query. It is not measurable from a query harness and is **not**
   evidenced here.

### 1.1 One number this document proposes, for ratification

§11.1 defines `query.maxCandidateDocuments` but gives it **no value**, and §22.9 defines the
error it raises (`413 CANDIDATE_LIMIT_EXCEEDED`). The measurements below make the choice
consequential, so it is raised rather than silently assumed:

> **PROPOSAL — `query.maxCandidateDocuments` cannot be set to 5,000.** At representative
> scale `article-type-list` (Tier A, `*[_type == "article"]{_id, title}`) materialises 5,833
> documents and `multi-type-list` materialises 6,333, because **the answer is that large**.
> A limit at the §35.16 top-of-range would reject two legitimate Tier A queries. Either the
> limit sits above the largest legitimate answer, or unbounded list queries must be paginated
> at the registry level. **This needs a decision; it is not resolved here.**

## 2. Representative scale, and why this one

The fixture dataset is 41 documents, which cannot distinguish a constant cost from a linear
one. Two independent sources fix the replacement.

**Count — PRD §35.16 *Performance tests*:** *"Type candidate sets of 100, 1,000, 5,000, and
configured maximum documents."* The top of the enumerated range is **5,000**. `configured
maximum` is §11.1's `maxCandidateDocuments`, which has no value (§1.1), so it cannot be
tested against.

**Shape — the Phase 0 audit** ([`audit/repository-audit.md`](../audit/repository-audit.md)):
*"article 32 (avg 915 B, max 952 B), author 5 (avg 241 B), page 3 (avg 591 B), siteSettings
1. Drafts: 2."* The audit is of a **greenfield** repository, so it supplies the document
shape and the type mix but not a production count — which is exactly why §35.16 has to supply
the count. The audit's own caveat is quoted in it: *"this is a greenfield audit … The audit
must be re-run against any real codebase that adopts the overlay."*

**Chosen scale:** **5,000 `article` documents at audit-measured size, with the audit-measured
type composition preserved** — 5,000 article / 833 author / 500 page / 1 siteSettings =
**6,334 documents, 5.13 MiB**. Generated article mean size is within 20 % of the audit's
915–952 B band, asserted in the suite.

Scaling articles *alone* was tried first and rejected during this work: it leaves a
three-document `page` type, and a work budget that a three-page type scan cannot breach is
not falsifiable for the page queries — the same vacuity trap
[`boundedness-2026-08-04.md`](boundedness-2026-08-04.md) §1 describes one level up. That is
why the composition is scaled, not just the one type.

**Determinism.** `spike-c/latency.ts` follows `fixtures/generate.mjs`: no `Date.now()`, no
`Math.random()`, no new dependencies. The corpus is a pure function of the committed fixture
and the requested count. Two invariants are asserted, both inherited from the 10× boundedness
harness and both learned the hard way there:

- every generated article sorts **strictly below** every original on `publishedAt` **and**
  `_createdAt`, so scaling changes the dataset without changing any top-K answer;
- slugs stay unique, so the parameterised slug lookups remain single-match at 5,000.

One addition: generated documents reference only generated documents, and originals only
originals. Reference expansion from an original therefore resolves the *same* targets at 30
and at 5,000 articles, so a change in materialised count can only come from the plan.

## 3. Method

Measured through the real `evaluateRegistered`, i.e. the whole §22.6 pipeline, phase by phase:

| phase | §22.6 | what it is here |
|---|---|---|
| `sim fetch` | step 5 | the harness **simulating** the server-side filtered base fetch by running the registered filter through `groq-js` over the whole base |
| `plan` | steps 1–4, 6–13 | candidate selection, branch union, tombstones, reference expansion, ordering |
| `evaluate` | step 14 | the **original** query through pinned `groq-js` over the candidate set |

`overlay = plan + evaluate` is the work the overlay itself adds. **`sim fetch` is excluded
from every verdict below.** In production that phase is a Sanity index lookup plus a network
round trip; here it is a full-dataset `groq-js` scan, so its wall clock (40–450 ms) is an
artefact of the simulator and would *overstate* local cost while *understating* network cost.
Its **document count** is kept and gated — that is the wire shape, and it is real.

Grid: 17 supported queries × 6 overlay fixtures at representative scale, the same grid at
fixture scale for the constancy comparison, plus 31 repetitions per query on the empty
overlay for the timing distribution (first run discarded as warm-up; §5.4 budgets the *warm*
case). Percentiles are nearest-rank, so every reported figure is an observed sample.

**Four independent 31-repetition runs were taken.** The machine was shared with concurrent
agents running their own suites, and total run time varied from 262 s to 610 s. The work
columns were **byte-identical in all four**; only the timings moved. Timing is therefore
reported as a **range**: p50 is the minimum across runs (the least-contended estimate of true
cost) and p95 is the maximum observed (the worst case seen). Command to reproduce:

```
SPIKE_C_LATENCY_REPS=31 SPIKE_C_LATENCY_OUT=/tmp/table.md \
  pnpm --filter sanity-overlay-testkit vitest run test/spike-c-latency.test.ts
```

### 4.2 Reading the table

- **The eleven small queries are not close to their budget.** 1–5 ms of local work against
  1,500–3,000 ms, with a candidate set of 0–29 documents that **does not grow between 30 and
  5,000 articles**. The §22.6 bounded plans hold at scale, including the top-K slices.
- **`article-type-list` / `multi-type-list` pass but thinly.** ~300–460 ms of *local* work,
  and 4.8–5.1 MiB of candidate documents that a real deployment must also transfer over the
  network — inside a 3,000 ms end-to-end budget. This is not a planner defect: the answer
  genuinely is every article, so the candidate set cannot be smaller than the response
  (`result-proportional` in [`boundedness-2026-08-04.md`](boundedness-2026-08-04.md)). It is a
  **product** finding: an unpaginated list query over a 5,000-document type is at the edge of
  §5.4 before the network is involved.
- **`articles-by-author-name` fails.** `*[_type == "article" && author->name == $name]`
  evaluated over 5,000 candidates costs **2.2 s at best and 12.7 s under load**, against a
  3 s end-to-end budget. The dereference-per-candidate inside `groq-js` — not the candidate
  count — is the dominant term: it materialises the same 5,833 documents as `article-count`
  (143 ms) and `stats-aggregate` (354 ms) but costs 6–15× more to evaluate.
- **`article-count` / `stats-aggregate` are at risk rather than failing.** They materialise
  the whole type (5,833 documents, 4.8 MiB) to return one number, but `groq-js` aggregates it
  cheaply, so the local cost stays inside budget. What breaks them is the **transfer**: 4.8 MiB
  over the network for a scalar. `stats-aggregate` reached 2,999.7 ms in one run — 0.3 ms inside its budget, on local work alone.

### 4.3 A finding that is not about latency

**`article-type-list` materialises 833 author documents it never uses.** The query is
`*[_type == "article"]{_id, title}` — it dereferences nothing — but the spike planner runs
reference expansion unconditionally. §22.6 step 8 is *"Analyze dereference paths"*, and the
spike planner does not implement the analysis. At representative scale that is 14 % of the
candidate set and ~0.7 MiB transferred for nothing, on the query that is already thinnest
against its budget. Pinned by a test so it cannot rot; **not fixed here** — the planner is
spike-grade and §0.6 forbids promoting it without a test-first rewrite.

## 5. The guard, and why it is not a stopwatch

`test/spike-c-latency.test.ts`, 297 tests. What it gates on:

| gate | assertion |
|---|---|
| **Constant work** | every `id-or-slug` query materialises the **same document count at 30 and at 5,000 articles**, and its base fetch returns the same count |
| **Absolute cap** | every `id-or-slug` query stays under 32 documents / 64 KiB (**proposed**, §5.1) |
| **Answer-proportional** | every list query selects no more than `answer size + branch delta`, where the answer is measured by a hand-written oracle that never reads the candidate plan |
| **Bounded top-K** | the three ordered slices materialise the same count at 30 and at 5,000 articles |
| **No N+1** | ≤ 2 `groq-js` invocations per query (§22.6 permits step 5 and step 14). The cap is asserted **tight** — some registered plan must actually use both, or the cap is vacuous |
| **Admissions** | the three `type-linear` queries must still scan their whole type and must still be Tier B; §22.6 step 8 must still be unimplemented. If a planner improvement fixes any of them the suite goes **red** and forces this document and `registry.ts` to be updated |

### 5.1 The proposed numbers, flagged for ratification

- `ID_SLUG_DOC_CAP = 32` documents, `ID_SLUG_BYTE_CAP = 64 KiB`. Deriving a document cap from
  a throughput model would be vacuous — 1.5 s of warm network buys megabytes — so the cap is
  **structural**: an id or slug lookup resolves one document plus what
  `maxReferenceDepth = 3` pulls in. The largest observed fan-out in this corpus is 9. 32
  leaves 3.5× headroom for a richer projection while still failing on the first step toward a
  type scan, which at this scale is 5,000.
- `MAX_EVALUATOR_INVOCATIONS = 2`, structural from §22.6.
- `query.maxCandidateDocuments` — see §1.1. **Unresolved.**

### 5.2 Why there is no wall-clock assertion

A wall-clock gate was **written, measured, and removed.** The draft gated the `id-or-slug`
class at half its §5.4 budget (750 ms) on the reasoning that those queries evaluate
single-digit document counts and measure about a millisecond — a claimed 700× margin.
Measurement refuted it:

> In a 31-repetition run, `pt-text` — **six** candidate documents, p50 **5.4 ms** — recorded a
> p95 of **348.9 ms**. `article-by-id` (nine documents, p50 1.3 ms) recorded 498 ms, a
> **529× spread** between its own fastest and slowest run on identical input.

The cause is that the same process allocates 5 MiB candidate sets for the type-list queries,
and the small queries absorb the garbage collector's pauses. The real margin was ~2×, not
700×, and on a loaded CI machine that gate would flake. Across four runs of the identical
suite, total duration ranged 262 s → 610 s purely from machine contention.

So the gate is **deterministic work**, which is causally upstream of time, and wall clock is
**evidence**. The suite still asserts the property that makes the split sound: work has
**zero** spread across repetitions while time does not. The `spread` column is emitted in the
report so the next reader can check that claim rather than trust it.

The residual risk is stated plainly: **a change that makes each document more expensive to
evaluate without changing any count would not be caught by the work gate.** The
`candidateBytes` proxy covers the "few but huge documents" version of that; a pure
per-document evaluation-cost regression is not covered, and the honest mitigation is that
`articles-by-author-name` — precisely such a case — was found by *measurement*, which is why
the measurement is in the suite even though it is not asserted on.

## 6. Mutation check

The guard is only worth its runtime if a materially worse planner breaks it. Two mutations
applied to `spike-c/planner.ts`, run, and reverted. Restoration verified by byte-comparison
against a pre-mutation copy (`diff` clean, sha256 `96cb4e96…` restored both times).

| mutation | what it does | result |
|---|---|---|
| **M1** — `base-filter` degraded to a full type scan | the pre-F6 defect: `article-by-slug` fetches 5,000 documents to return 1 | **36 tests failed** — constancy (12), absolute cap (12), and the answer-proportional budget for `filter-by-tag` and `references-author` (12) |
| **M2** — top-K over-fetches `K + datasetSize/10` | an ordered slice whose candidate set grows with the dataset | **18 tests failed** — the three top-K queries across all six overlays, on both the constancy and the proportionality gates |

Restored after each: **297 / 297 green.**

Note which gate caught M1: the **constancy** comparison and the **absolute cap**, not the
answer-proportional one — a slug lookup returning 1 document out of a 5,000-document scan
still satisfies "no more than the answer plus the delta" only because the scan *is* bounded by
the type. This is the F6 lesson reproduced: a budget expressed in terms the implementation
also computes cannot falsify the implementation. The constancy check is implementation-
independent by construction, because it compares the planner against **itself at another
scale**.

## 7. Verdict for Gate D

PRD §36.3 pass criterion 5: *"Preview latency stays within budget on representative data."*

**Met for 14 of 17 supported queries; not met for 3.** Per query:

- **PASS with two to three orders of magnitude of margin (11 queries)** — every `id-or-slug`
  query, every bounded top-K slice, `filter-by-tag`, `references-author`. Candidate sets of
  0–29 documents that are provably **constant between 30 and 5,000 articles**. §22.6's bounded
  candidate claim holds at representative scale.
- **PASS, thin margin (2 queries)** — `article-type-list`, `multi-type-list`. ~300–460 ms of
  local work plus ~5 MiB of transfer inside a 3,000 ms end-to-end budget. Tier A is correct
  (the cost is the answer), but they are the queries to watch as the dataset grows, and they
  are the reason `maxCandidateDocuments` cannot be set at 5,000 (§1.1).
- **AT RISK (2 queries)** — `article-count`, `stats-aggregate`. Tier **B**. Local evaluation
  fits, but they transfer 4.8 MiB to return a single scalar. **PRD justification:** §22.6
  step 14 hands the **original** query to `groq-js` over the candidate set, so an aggregate is
  only correct if every aggregated document is present. **Fix:** aggregate pushdown — evaluate
  `count()` / `math::sum()` against the base and apply the overlay delta arithmetically — a
  planner capability §22.6 does not specify. **Named a Phase 6 concern**, unchanged from
  [`boundedness-2026-08-04.md`](boundedness-2026-08-04.md) §5.
- **FAIL (1 query)** — `articles-by-author-name`. Tier **B**. 2.2 s of local work at best,
  12.7 s under contention, against a 3,000 ms end-to-end budget. **PRD justification:** the
  filter traverses a reference, so membership depends on a field of the *target*; no base-side
  predicate over articles is complete once an author is edited, and **§22.7 itself specifies
  this plan as "Base candidates: all articles"** — the scan is PRD-sanctioned. **Fix:** §22.6
  step 10 (reverse-reference expansion over touched targets) would bound the candidate set by
  the *referrer count* of the touched targets. Note this fixes the count but the measurement
  says the dominant term is the **per-candidate dereference inside `groq-js`**, so bounding
  the count is exactly the right lever: 5,000 → tens of candidates removes both.

**Abort threshold (§0.6 / §22.12): not approached.** The threshold is about **Tier C**
queries. Tier C count remains **1** (`unconstrained-star`, a deliberate structural-failure
probe), unchanged by this work, and **zero queries moved to Tier C**. All three latency
findings are already-accepted **Tier B**, which Gate D admits ("Tier A or *accepted* Tier B").

**What this does not close.** §5.4's budgets are end-to-end and this harness measures only
the in-process part; the network, serialisation and transport terms are unmeasured, and the
*Preview refresh after edit* row is not evidenced at all. The three findings above are
therefore **lower bounds on cost**, not estimates of it — a deployed measurement can only make
them worse. `gate-review.md` and `report.md` are owned by the orchestrator; **this document
does not edit them.**

## A.1 Aggregate pushdown

§4.1 measured `article-count` and `stats-aggregate` materialising **5,833 documents / 4.8 MiB
to return one scalar**. The cause was structural and is stated correctly in §7: §22.6 step 14
hands the **original** query to `groq-js` over the candidate set, so an aggregate registered
under a document-returning plan must materialise everything it aggregates.

**The fix is a partition, not an estimate.** The virtual dataset is exactly

```
{base documents the branch did not touch}  ∪  {resolved branch records}
```

and `count()` and `math::sum()` are **additive over a partition**. So the base evaluates the
same aggregate with `!(_id in $__touched)` appended and returns **one number**; the candidate
set is the branch delta alone; the two halves are added. Every document is aggregated in
exactly one half, so **the answer is exact, not approximated** — which is the whole point,
because §5.5 forbids returning a plausible number.

**What is refused rather than approximated.** `math::avg`, `math::min`, `math::max` are *not*
registrable: recombining them needs a second scalar this port does not carry. An aggregate
whose filter **dereferences** is also refused — the base half decides membership from the base
state, so editing a reference *target* would move documents between the halves without the
base knowing, and the sum would stop being the answer. Both raise the structured
`UNSUPPORTED_GROQ`.

## A.2 Reverse-reference expansion (§22.6 step 10)

§4.1 measured `articles-by-author-name` at **p50 2,236 ms / p95 12,691 ms** against a 3,000 ms
budget — the one outright **FAIL**. §7 correctly noted that §22.7 *specifies* this plan's base
candidates as "all articles", so the scan was PRD-sanctioned rather than a defect.

The scan is nonetheless avoidable, because the incompleteness has exactly one source. Take any
virtual article `A` in the answer:

| case | why it is still found |
|---|---|
| `A` is touched | a branch record of the type, admitted by §22.6 step 6 |
| `A` untouched, target untouched | both resolve to their base rows, so the **base-state disjunct** selects it |
| `A` untouched, target touched | `A` references a touched ID, so the **`references($__touched)` disjunct** selects it |

**There is no fourth case**, so nothing in the answer is missed. Both disjuncts travel in
**one** base fetch, which keeps the query inside §22.6's step-5-plus-step-14 evaluation budget;
asking for the matching targets and then for their referrers would be two round trips for one
candidate set.

**This stays Tier B, and that is not a hedge.** The bound is the *referrer fan-out of the
branch* — a property of the data, not a constant. A branch that touches every author still
pulls in every article. Tier A requires a bound from the query's own semantics; this one is
bounded by the blast radius, so **B is the honest tier**. What changed is that it is now
bounded at all.

**Refused rather than approximated:** more than one dereference hop. With `a->b->name`, an
untouched referrer whose *grandchild* was edited references neither the edited document nor
anything the base half can see, so `references($touched)` would miss it. Measured on the parsed
AST, not by string matching.

## A.3 Dereference-path analysis (§22.6 step 8)

§4.3 recorded that `article-type-list` materialised **833 author documents it never
dereferences**, because the spike planner ran reference expansion unconditionally. The
analysis now reads the parsed query, reports the attributes a `->` is applied to, and reports
*"follow everything"* when it cannot resolve one — over-approximating costs candidates,
under-approximating would lose documents, so the failure direction is chosen deliberately.

The implementation is the one already written and tested in
`packages/sanity-overlay-query/src/derefPaths.ts`, **reused** by the spike harness rather than
re-implemented, so this evidence measures shipping behaviour.

> **Correction to §4.3.** §4.3 estimated the waste at *"~0.7 MiB transferred for nothing"*.
> Measured, it is **235 KiB** (4,946.8 → 4,711.8 KiB). The document *count* claim was right
> — 833 documents, 14 % of the candidate set — but authors are much smaller than articles, so
> by bytes it was 4.8 %, not 14 %. The original figure was an estimate presented without being
> measured; this is the measurement.

## A.4 Results — before and after, same harness, 31 reps

`docs` = documents handed to `groq-js` at step 14; `refs` = reference expansion; `KiB` =

number for that case: with no branch there is no branch delta, so the aggregates transfer *no
documents at all* and the reverse-reference fetch matches nothing. It is **not** a claim that
these queries are free under a branch. Under a branch each materialises its branch delta, and
that is what the boundedness suite gates on — with a ceiling derived from the overlay and the
query semantics, never from a planner constant.

### A.4.1 One number that got worse, and why it is a harness artefact

`articles-by-author-name`'s **simulated base fetch** rose to a p50 of **576 ms**. That column
is the harness running the base filter through `groq-js` over the whole 5,000-document base
in-process; a real deployment answers it from a Sanity index over the network. The
`sim fetch` column was already flagged as a harness artefact in the §4 table notes and is
excluded from `overlay share` for exactly this reason.

Stated plainly so it cannot be read as spin: **even counting that artefact in full**, the
query's total p95 is **1,594.6 ms against a 3,000 ms budget**. Before the fix, the *overlay
half alone* was 12,691 ms. The query is inside budget on the pessimistic reading as well as
the correct one.

## A.6 The canonical proof still holds, with counts

§5's split between parity and boundedness rests on a **negative** claim: parity is preserved by
any *superset* of the correct candidate set, so it cannot detect over-fetching. That was prose;
it is now executed in `spike-c-parity.test.ts`. Every registered plan was replaced with a
maximally unbounded one (`types` over **every** type in the dataset) and run through the real
evaluator:

| measure | result |
|---|---|
| cases (17 supported queries × 6 overlay fixtures) | **102** |
| parity agreements with the full-dataset oracle | **102 / 102** — parity is completely blind |
| cases where the unbounded planner materialised strictly more | **102 / 102** |
| documents materialised, unbounded vs registered | **3,978 vs 694** (5.7×) |
| boundedness ceiling violations (`spike-c-boundedness.test.ts`) | **102 / 102** |

So the unbounded planner is **invisible to parity and rejected by every boundedness ceiling** —
which is the property the two-suite split exists to have.

The proof carries its own liveness control, without which it could pass because the equality
check is broken rather than because parity is blind: the same unbounded planner compared
against a **branch-blind** oracle disagrees on **23** cases. The comparison discriminates.

## A.7 Verdict for Gate D

PRD §36.3 pass criterion 5: *"Preview latency stays within budget on representative data."*

**Met for all 17 supported queries.** §7's split was 11 PASS / 2 PASS-thin / 2 AT RISK /
1 FAIL. It is now:

- **PASS, large margin (15 queries)** — every `id-or-slug` query, every bounded top-K slice,
  `filter-by-tag`, `references-author`, and **all three former misses**. `article-count`,
  `stats-aggregate` and `articles-by-author-name` now transfer nothing on an empty branch and
  the branch delta otherwise, at single-digit milliseconds of overlay work.
- **PASS, improved margin (2 queries)** — `article-type-list`, `multi-type-list`. §22.6 step 8
  removed 833 unused documents each; p95 fell 1,891 → 72 ms and 2,858 → 105 ms. **Still the
  queries to watch**: the cost is the *answer*, which no planner can shrink, and §1.1's
  `maxCandidateDocuments` proposal is **still unresolved** — this addendum does not close it.
- **AT RISK: none. FAIL: none.**

**Tier changes.** `article-count` and `stats-aggregate` move **Tier B → Tier A**: their
candidate set is now the branch delta, which is §22.3 Tier A's *"counts and aggregates over a
proven finite candidate set"*. `articles-by-author-name` **stays Tier B** on purpose — see
§A.2. Tier C count remains **1**. **No query moved to Tier C.**

**Exactness.** Every fix is exact, and every case that cannot be proven exact is **refused**
with the structured `UNSUPPORTED_GROQ` rather than approximated: non-additive aggregates,
aggregates whose filter dereferences, and reverse-reference filters with more than one hop.
No result in this addendum is an estimate.

**What this still does not close**, unchanged from §7: §5.4's budgets are end-to-end and this
harness measures the in-process part only. Network, serialisation and transport remain
unmeasured, and *Preview refresh after edit* is still not evidenced. These numbers remain
**lower bounds on cost**. `gate-review.md` and `report.md` are owned by the orchestrator;
**this document does not edit them.**

### A.7.1 Status of the production package

The spike planner is §0.6 throwaway evidence code and **must not be promoted**. The two
pushdown plans were therefore re-implemented test-first in
`packages/sanity-overlay-query` (`planner.ts`, `evaluate.ts`, `derefPaths.ts`), where they are
proven exact against a full-dataset oracle across every parity overlay
(`test/query-pushdown.test.ts`). §22.6 step 8 was already shipping there and is what the spike
harness now reuses.

The three query *registrations* remain deliberately **absent** from `M_LOCAL_QUERIES`, and
that absence is still pinned by `query-registry.test.ts`. The reason has changed and the pin
now records the new one: it is no longer a **capability** gap but a **§22.5 registration**
decision — registering a query also pins a parity fixture and a `maxCandidates`, and for the
reverse-reference shape that limit is the unratified branch-blast-radius number of §1.1.
