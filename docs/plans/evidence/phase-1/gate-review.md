## Recorded risks (not gate failures)

1. **HTTP/1.1 connection starvation (Gate A).** The proxy speaks plain HTTP/1.1. Studio's own SSE listeners exhaust Chrome's 6-connection per-host limit and starve subsequent requests; this crashed the structure tool in a live session. Boundary reproduced exactly: 5 streams complete, **6 never do**. Real Sanity avoids this via HTTP/2 multiplexing. **Deliberately not patched** — bounding the listeners trades a load-dependent hang for permanent read-only flicker plus a refetch storm, and serving h2 would rewrite the security boundary's transport and require re-implementing the WS frame guard on RFC 8441 extended CONNECT. Decision needed before any Gate A sign-off that assumes interactive stability.
2. **`article-type-list` materialises 833 authors it never dereferences** — §22.6 step 8 ("analyze dereference paths") is unimplemented. 14% of its candidate set on the query already thinnest against budget. Pinned by test, not fixed (spike-grade planner).
3. **~~Token refresh is modelled but never invoked~~ — CLOSED 2026-08-04.** Wired to Studio's own definition of authenticated (`!!currentUser?.id`, `WorkspaceLoader-BRx2afZV.js:2542`), piggybacking on the `/users/me` round trip Studio already performs after `refreshWorkbenchToken()` reissues a token — no polling added. Eight credulity guards are pinned, because `/users/me` answers an unauthenticated caller with HTTP 200 and a `null` body: a public GROQ 200, `/ping`, an arbitrary 200, and a `null`/`{name}`/empty-`id` body all leave the session refusing writes. Logout remains terminal.
4. **~~Three TLS claims are object-asserted only~~ — CLOSED 2026-08-04.** All three are now proven against live TLS sockets using certificates minted in-test with `node:crypto` (no new dependencies), with every case running the production dial path rather than an injected dialler. A client frame now crosses a real TLS leg, so the WebSocket frame guard is exercised on the transport it uses in production. **Correction that came out of it:** the code was right but its stated rationale was wrong — Node's `TLSSocket` buffers pre-handshake writes, so proceeding on `connect` does not leak bytes early; the actual exposure is that the head carrying `Authorization: Bearer` would be handed to a socket whose peer certificate is not yet verified. The tests now assert that narrower, true claim. **Still unproven:** that `tls.connect` succeeds against the real `<project>.api.sanity.io:443` with the *public* root store and Sanity's own ALPN behaviour — every certificate in the suite is one the test minted.
