## 1. What you can actually do now

### Mode 1 — your existing Sanity project

```ts
// sanity.config.ts
import {defineOverlayConfig} from 'sanity-overlay-studio'
import {structureTool} from 'sanity/structure'
import {schemaTypes} from './schemaTypes'

export default defineOverlayConfig({
  name: 'default',
  projectId: 'xxxxxxxx',
  dataset: 'staging',
  plugins: [structureTool()],
  schema: {types: schemaTypes},
})
```

Change `defineConfig` → `defineOverlayConfig`, run the overlay API, done. No `unstable_clientFactory`, no localStorage flags. `OVERLAY_MODE=off` restores stock Sanity byte-for-byte.

**It is not `plugins: [overlay()]`** — `unstable_clientFactory` is declared on `SourceOptions`, not `PluginOptions`, so a plugin *cannot* set it. A plugin-shaped API would have type-errored and been silently ignored, taking the entire write-blocking guarantee with it. `overlay()` still ships for the subset a plugin genuinely can do.

### Mode 2 — no Sanity project at all

```bash
node --experimental-strip-types examples/kitchen-sink/spikeB-proxy/runOrigin.mjs \
  --origin --root=examples/kitchen-sink --port=3999
```

Then point Studio at it (`SANITY_STUDIO_OVERLAY_API_HOST=http://localhost:3999`). Identity is a synthetic `local-dev` user with full grants — **a stub, not an auth system**. It refuses any non-loopback bind, with no override flag.

### The stack

```bash
cd examples/kitchen-sink
pnpm dev                                                # Studio      :3333
PROXY_BLOCK_WRITES=1 node spikeB-proxy/proxy.mjs        # proxy       :3999   (Mode 1)
pnpm overlay:server                                     # overlay API :3998
pnpm --filter local-site dev                            # site        :4000
```

CLI: `packages/sanity-overlay-cli` — `inspect · status · validate · diff · reset · rebase · conflicts · query · export · import`.

## 3. Known gaps — the honest list

1. **Studio's structure list is empty in Mode 2.** It uses a *findability* query (`text::query` + `references`), not a type-list query; origin mode doesn't implement it, and with no upstream to fall back to that means an empty pane. A fix is in flight. The data layer is fine — a type-list query returns both documents correctly.
2. **The plugin has no overlay-aware GROQ reads of its own.** It substitutes `getDocument`/`getDocuments` from the session echo map; `fetch` is delegated. ## 4. Defects found overnight — worth reading

These were all invisible to a passing suite:

- **The Studio plugin could never have been installed.** `src/index.ts` imported `@sanity/client` without declaring it — `ERR_MODULE_NOT_FOUND` at boot on your machine, hidden in-repo because the workspace root hoists. Now a **peer** dependency: a hard dependency would give you a second client copy, so the facade would wrap a different class than Studio holds and intercept nothing.
- **Four version-write methods escaped the facade entirely.** `createVersion`, `replaceVersion`, `discardVersion`, `unpublishVersion` called `_dataRequest` directly on both surfaces, so no guard could see them — and Sanity 6.8.0 calls all four from its own hooks. A path to staging. Now refused.
- **A reverse-reference dedup collision made a strongly-referenced document deletable**, violating invariant §34.10. Root cause: joining key parts with a separator — `k` and `k+S+k` collide. The same construction silently dropped a genuine keyed-array reorder (zero operations emitted). Fixed structurally in four places.
- **A mutation artifact was staged in the git index** and would have been committed. It survived my repo-wide sweep because the file contained NUL bytes, so git classified it as *binary* — `git diff` printed only "Binary files differ" and `grep` skipped it. There is now a repo-wide control-byte guard that scans the index.
- **The test suite was making a live write to Sanity** on every run (`POST .../assets/images/parity`), harmless only because the token lacked permission. Removed; verified across three runs with a transport monitor — 455 outbound requests, 13 remote, all GET.
  **Follow-up, 2026-08-05:** that one-file monitor is now permanent and suite-wide (`packages/sanity-overlay-testkit/vitest.setup.ts`), and it *enforces* rather than measures — a non-GET to a `sanity.io` host fails the suite wherever it is attempted.
